Tổng quan: một câu hỏi đi qua hệ thống như thế nào

Người dùng gõ câu hỏi về Luật Doanh nghiệp. Hệ thống tìm Điều/Khoản liên quan, đưa cho LLM viết câu trả lời có citation, kiểm lại citation, rồi hiển thị lên giao diện. Người đọc có thể bấm từng bước dưới đây để xem bước đó làm gì và thuộc team nào.

Team 1 — Data & Retrieval

Team 1 xây corpus pháp luật, chunking, BM25, dense retrieval, Hybrid RRF, Golden set và đánh giá retrieval.

Team 2 — RAG & LLM

Team 2 phụ trách reranker, context builder, prompt, LLM client, citation verification và benchmark chất lượng câu trả lời.

Team 3 — Fullstack

Team 3 làm backend Spring Boot, REST API/SSE, frontend React, document viewer và đo latency end-to-end.

Phần dùng chung

Cả ba team cùng giữ contracts/, docs/, tests/ và quy trình PR vào develop.

Dữ liệu pháp luật: từ văn bản gốc đến chunk

Team 1

Phần này biến văn bản luật thành dữ liệu mà retrieval đọc được. Mọi phần phía sau đều phụ thuộc vào chất lượng của bước này.

Team 1 lưu corpus chính trong data/doanh-nghiep/. Corpus này gồm 8 văn bản: Luật Doanh nghiệp 59/2020/QH14, Luật 76/2025/QH15, các Nghị định 122/2021, 168/2025, 288/2026, Thông tư 68/2025/TT-BTC và hai văn bản hợp nhất (VBHN 67 và VBHN 7566).

Mỗi văn bản đi qua ba tầng folder. Folder raw/ giữ bản gốc tải về, folder interim/ giữ text đã làm sạch, và folder processed/ giữ kết quả cuối cùng. File registry/documents.json lưu metadata của từng văn bản như số hiệu, loại văn bản và tình trạng hiệu lực.

Script chunk_documents.py đọc interim/ cùng registry, cắt văn bản theo đơn vị Khoản, rồi ghi ra processed/chunks.jsonl với 2.576 chunk. Từ tuần 10 (VLRA-71), script này còn ghi thêm processed/articles.jsonl với 635 Điều nguyên văn cho Article Store. Trước đó, Viewer phải nối chunk lại thành Điều nên bị lặp câu dẫn ở 48 Điều và mất chú thích sửa đổi ở 46 Điều.

Team 1 còn có corpus mở rộng trong data/doanh-nghiep-mo-rong/. Script build_from_hf.py tạo corpus này từ một dataset trên Hugging Face, gồm 1.000 file text trong interim/ và file nén processed/chunks.jsonl.gz. Script scripts/preprocess_legal_data.py và scripts/validate_chunks.py lần lượt làm sạch dữ liệu và kiểm tra schema của chunk.

Retrieval: tìm đúng Khoản cho mỗi câu hỏi

Team 1

Retrieval quyết định LLM được nhìn thấy gì. Nếu chunk đúng không lọt vào top-k, LLM không thể trả lời đúng dù prompt tốt đến đâu.

Team 1 viết package team1_data/retrieval/ với ba cách tìm kiếm. File bm25.py chạy BM25 kiểu Lucene (k1 = 1,2, b = 0,75) trên token do tokenizer.py tách bằng underthesea. Hai file embedding.py và dense.py chạy dense retrieval với model AITeamVN/Vietnamese_Embedding và khoảng cách cosine. File hybrid.py gộp hai danh sách bằng RRF với k = 60 và trọng số BM25 : Dense = 0,5 : 1.

File retrieval_v2.json ghi cấu hình đã chốt ở VLRA-53, trả về top_k = 20 từ tối đa 100 ứng viên. Team 2 đọc file này khi dựng runtime. Script scripts/populate_qdrant.py nạp embeddings đã tính sẵn vào Qdrant để không phải encode lại toàn bộ corpus.

Folder evaluation/retrieval/ lưu cấu hình thử nghiệm trong configs/ và kết quả từng lượt chạy trong runs/ (từ vlra49 đến vlra53-aiteamvn-weights). Mỗi lượt chạy ghi commit, sha256 của Dev Set và corpus, nên hai lượt chỉ được so sánh khi hai hash này trùng nhau.

Golden set: bộ đề chuẩn để chấm điểm

Team 1 soạn · Team 2 review

Golden set là bộ câu hỏi có sẵn đáp án chuẩn. Cả retrieval lẫn RAG đều được chấm trên cùng bộ này, nên một lỗi ở đây làm sai mọi con số phía sau.

Team 1 giữ bộ Dev Set trong team1_data/golden/golden_phase1.json với 110 câu. Mỗi câu ghi gold_chunk_ids (các Khoản chứa đáp án), expected_status và review_status. Ở tuần 10, Team 1 đóng băng bộ này (PR #57): mọi câu có split: "dev" và relevant_unit_groups, còn hash sha256 được ghi trong golden_phase1.manifest.json. Hash được tính trên JSON đã chuẩn hóa NFC nên không đổi khi ai đó chỉ sửa khoảng trắng.

File out_of_scope_v1.json chứa 33 câu ngoài phạm vi, dùng để Team 2 chỉnh cổng từ chối trả lời. File edge_cases_v1.json chứa các ca biên như câu hỏi mơ hồ hoặc nhắc lượt trước.

Module team1_data/evaluation/ chạy bằng lệnh python -m team1_data.evaluation check hoặc run. Lệnh check kiểm schema, kiểm gold có tồn tại trong corpus và in hash. Lệnh run tính Recall@k, MRR@20, hit@5 rồi ghi kết quả vào evaluation/retrieval/runs/.

RAG & LLM: từ chunk thành câu trả lời có citation

Team 2

Team 2 nhận top-k chunk từ retrieval, chọn context, viết prompt, gọi LLM và ép output về đúng contract cho Team 3.

File team2_rag/runtime.py đọc biến môi trường như RAG_RERANK, RAG_BM25_ONLY, RAG_TOP_K và timeout rerank 4 giây, rồi lắp các thành phần lại với nhau. File reranker.py chấm lại chunk bằng model BGE, nhưng Team 2 đã tắt rerank mặc định (RAG_RERANK=false) vì Hybrid thắng hoặc hòa ở mọi chỉ số trên 110 câu.

Folder prompts/ dựng phần đầu vào cho LLM. File context.py gắn nhãn C1..Cn và metadata cho từng chunk, đồng thời giữ ngân sách token. File templates.py chứa System Prompt prompt_v3, yêu cầu LLM chỉ trả lời từ context, nêu điều kiện và ngoại lệ, và trả insufficient_context khi thiếu căn cứ.

Folder llm/ có client cho Gemini, Ollama, OpenAI và Qwen, được chọn qua factory.py. File output_parser.py ép output về JSON gồm status, answer, citations và claims (field claims chỉ dùng nội bộ để kiểm chứng). File pipeline.py nối Retrieval → Context → LLM → Verification, còn answer.py kiểm citation có khớp chunk đã gửi rồi đánh lại nhãn.

Folder api/ mở HTTP API cho backend Java: app.py chạy pipeline thật, còn mock_app.py trả dữ liệu giả để Team 3 phát triển song song. Team 2 đang dùng LLM gemini-3.1-flash-lite.

Verification & benchmark: citation có thật sự chứng minh câu trả lời?

7

Fullstack: backend Java, frontend React và Viewer

Team 3

Team 3 đưa pipeline đến người dùng: nhận câu hỏi, gọi Team 2, stream câu trả lời, hiện citation và mở nguyên văn Điều luật.

Folder backend/ là ứng dụng Spring Boot build bằng Maven. Package ai/ gọi API của Team 2 qua HttpAiClient và đổi DTO từ snake_case sang camelCase. Package chat/stream/ phát SSE cho frontend. Package conversation/ lưu hội thoại bằng JPA, với schema trong resources/db/chat-schema.sql. Package document/ phục vụ Viewer mở một Điều, còn common/ gom exception và mã lỗi public.

Backend có hai profile. Profile application-mock.properties dùng AI giả và H2 để chạy nhanh khi dev. Profile application-rag.properties gọi RAG thật và dùng PostgreSQL.

Folder frontend/ dùng React 18, Vite, TypeScript và Tailwind 4. Folder src/api/ có chatStream.ts và sse.ts để đọc stream, retryPolicy.ts để thử lại khi lỗi mạng, và errorText.ts để hiện thông báo lỗi thống nhất.
